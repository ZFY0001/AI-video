# 剧本 → 分镜：拆解层设计

> **状态**：A 期、B 期、C 期均已落地。
> **范围**：只做"拆解"这一层——把一句话到分镜的过程变成可看、可改、可局部重跑。不碰出图、不碰一致性锚定、不碰局部重绘。
> **约束**：`pipeline/models.py`、`app/engine.py`、`app/gui.py` 与 Web 端都在用这些结构，改动必须向后兼容旧的分镜文件。

---

## 一、现在的问题

管线其实已经分了三段：简报（`brief`）→ 剧本（`script`）→ 分镜（`storyboard`），进度条上 `0.10 / 0.16 / 0.22` 三个节点就是它们。`Script` 和 `Storyboard` 也都是正式的数据类，不是临时字典。

问题不在"有没有拆"，在于**拆完就没了**：

1. **看不到。** 剧本和分镜都在工作线程里生成，直接喂给下一段。用户能看到的只有日志里几行字，和最后成片。想审一下分镜对不对，只能等整条管线跑完——十几分钟，然后从结果反推。
2. **改不了。** 分镜一旦生成就固化在 `board.shots` 里，没有任何入口能让用户把第 3 镜从 4 秒改成 6 秒、把"俯拍"改成"平视"、或者删掉一镜。要改只能改提示词整体重跑，还不保证别的镜头不变。
3. **没留下"为什么"。** `Shot.act` 只存了一个场次名字符串，没有指向剧本里的哪一段、哪一句。所以"这一镜是从哪来的"这个问题，事后答不出来。

一句话：**拆解的质量没法被检验，因为拆解的过程不可见。**

## 二、目标

把"一次跑完"拆成"先拆、再拍"两段，中间给人一个可以插手的位置：

```
输入一句话
   ↓
① 拆解（plan）  简报 → 剧本 → 分镜      秒级，不渲染，可反复
   ↓  ← 这里可以看、可以改、可以只重拆某一场
② 拍摄（render） 逐镜出图 → 质检 → 合成   分钟级，不可反复
```

三条硬要求：

- **拆解必须能单独跑**，且不产生任何图片/视频，只写 JSON。一次拆解应在 10 秒内返回（一次 LLM 调用）。
- **拍什么由文件决定，不由内存决定。** 拍摄阶段从 `plan` 文件读分镜，所以用户改完文件就生效——这是"可编辑"能成立的唯一前提。
- **每一镜都能追溯到剧本的某一句。** 不是为了好看，是为了第二项（跨镜头一致性）和第三项（局部重绘）将来能定位"改这里会连累谁"。

## 三、数据契约的改动

### 3.1 `Script`：把 `acts` 从"名字列表"变成"结构"

现在 `Script.acts` 是 `list[dict[str, str]]`，实际上只有 `{name, summary}`。扩成：

```python
@dataclass
class Beat:
    beat_id: str          # "a1.b2"，场次内唯一
    kind: str             # 建立 / 铺垫 / 转折 / 高潮 / 收束
    text: str             # 这一拍要说什么、给什么信息
    est_seconds: float    # 预估时长，分镜时作为分配权重的依据
    subject_ids: list[str] = field(default_factory=list)

@dataclass
class Act:
    act_id: str           # "a1"
    title: str
    intent: str           # 这一场的叙事目的（一句话）
    beats: list[Beat] = field(default_factory=list)
```

`Script.acts` 的类型改成 `list[Act]`，序列化时用 `asdict`。**兼容**：读旧文件时 `acts` 里是扁平 dict，用 `Act(**{k: v for k, v in d.items() if k in FIELDS})` 兜住，缺 `beats` 就按一整拍处理。旧分镜不重算，只在打开时补默认值。

### 3.2 `Shot`：加三个来源字段

```python
act_id: str = ""          # 属于哪一场
beat_ids: list[str] = []  # 覆盖了哪几拍（一镜可跨拍）
source_line: str = ""     # 剧本里的原句，用于"这镜是从哪来的"
```

这三个字段只增不改，旧分镜反序列化时为空，界面显示"来源未知"而不是报错。

### 3.3 落盘

`runs/<run_id>/` 下新增两个文件，与现有 `output/storyboard.json` 并存：

| 文件 | 内容 | 谁写 |
|---|---|---|
| `plan/brief.json` | `ProjectBrief` | 拆解阶段 |
| `plan/script.json` | `Script`（含 acts/beats） | 拆解阶段 |
| `plan/storyboard.json` | `Storyboard`（含 provenance） | 拆解阶段，**拍摄阶段读它** |
| `plan/meta.json` | 拆解用的模型、耗时、是否被人工编辑过 | 两阶段都写 |

`plan/meta.json` 里记一个 `edited: {script: bool, shots: [镜号]}`，界面据此标出"哪些是你改过的"。这个字段看起来多余，但没有它，重跑之后就分不清"这是模型的判断还是我的修改"。

`output/storyboard.json` 保持不变——它仍然是成片附带的产物，拍摄阶段把它从 `plan/` 拷过去，保证老代码（读 output 的那几处）不受影响。

## 四、引擎改造：一次跑完 → 两段

现在 `Engine.start()` 一口气走到合成。拆成两个入口，内部复用同一条 `_process_shot`：

```python
class Engine:
    def plan(self, opts) -> PlanResult:      # 新增：只到分镜为止
        brief = self._brief(opts)
        script = self._script(brief, opts)
        board = self._storyboard(brief, script, opts)
        self._persist_plan(brief, script, board)
        return PlanResult(brief, script, board)

    def render(self, plan_dir: Path, opts) -> RunResult:   # 新增：从文件拍
        board = Storyboard.load(plan_dir / "storyboard.json")   # ← 关键：读文件，不读内存
        ...逐镜 process → 终检 → 合成
```

`start()` 保留为 `plan()` + `render()` 的串联，Tkinter 版和现有 API 因此完全不受影响。

**`render()` 必须重新做三件事**，否则用户改了分镜会得到自相矛盾的结果：

1. `build_timeline()` 重算 `start` 与总时长——用户可能改了某镜时长，累加会变。
2. `_enforce_narration_pacing()` 重跑——台词与镜长要对得上。
3. 校验镜数与时长的上下限（`MIN_SHOT_SECONDS` / `MAX_SHOT_SECONDS`），越界就报错并指出是哪一镜，**不静默修正**。用户改的值被系统偷偷改掉，比不支持编辑更糟。

## 五、接口

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/api/plan` | 只拆解，返回 run_id + script + shots，不渲染 |
| `GET` | `/api/plan/{run_id}` | 读回三个文件（界面刷新用） |
| `PATCH` | `/api/plan/{run_id}/script` | 改剧本（场/拍文字、时长），返回"哪几镜受影响" |
| `PATCH` | `/api/plan/{run_id}/shots/{shot_id}` | 改单镜（`duration` / `visual` / `camera` / `narration`） |
| `POST` | `/api/plan/{run_id}/render` | 用这份 plan 出片（走现有 SSE 事件流） |

`PATCH script` 不自动重派生全部镜头——那样用户刚改好的镜头会被冲掉。默认只标 `stale: true` 并列出受影响镜号，由用户决定"重拆这几场"还是"就这样拍"。这是一个刻意的选择：**自动重派生看起来智能，实际上会吃掉人的工作。**

## 六、界面

### 6.1 拆解页（新）

三栏，从左到右是"越拆越细"：

```
┌─────────────┬───────────────────────────┬──────────────┐
│ 剧本         │ 节拍                       │ 将拆成        │
│ 标题/一句话  │ a1 建立                   │ 6 镜 · 18 秒  │
│ 基调         │  ▸ b1 夜色铺开  3.0s      │              │
│             │  ▸ b2 街口人声  3.0s      │ 镜1 a1.b1 3s │
│ a1 建立      │ a2 转折                   │ 镜2 a1.b2 3s │
│ a2 转折      │  ▸ b1 雨落下来  4.0s      │ …            │
│ a3 收束      │                           │              │
└─────────────┴───────────────────────────┴──────────────┘
```

- 左栏点一场，中栏显示这一场的节拍，右栏实时显示"这一拍会变成几镜"。
- 节拍可直接改文字与时长，失焦即保存（`PATCH script`），右栏的预估随之变。
- 顶部只有一个主按钮：**开始拍摄**。它不是"重新生成"——它承诺的是"按你现在看到的分镜去拍"。

### 6.2 分镜表（拆解页的第二个视图）

表格而非卡片。每行一镜，列：镜号 / 来源（`a2.b1`）/ 时长 / 画面 / 机位 / 台词。时长与文字可直接改，改过的行左侧有竖条标记。

行尾一个"仅重拍这一镜"——这一项不在这期做，但位置先留出来，因为它决定了表格里必须能定位到单镜。

### 6.3 与现有页面的关系

拆解页是**创作台的前置**，不是第四页。流程改成：写一句话 → 点"拆解" → 在拆解页审改 → 点"开始拍摄" → 回到创作台看进度。创作台里原来那个"开始生成"按钮保留，走一次跑完的老路径，两种用法并存。

## 七、校验与不变量

拆解层必须保证以下四条，任一条不满足就拒绝进入拍摄：

1. **时长自洽**：`Σ shot.duration == project.total_duration`（浮点容差 1e-3）。
2. **镜数上下限**：至少 1 镜；单镜时长在 `[2, 10]` 秒内。
3. **台词不漏**：`Script.narration_full` 的每一句都必须被至少一镜的 `narration` 覆盖——现在靠 `distribute_narration` 分配，人工改台词后可能漏句。
4. **来源可解析**：每个 `beat_id` 都能在 `script.json` 里找到对应节拍。找不到就降级成"来源未知"，不报错。

第 3 条是新增的，也是最容易出的问题：删掉一镜之后，它原来承担的那句话就没人说了。

## 八、验收标准

- 一句话输入 → 拆解在 **10 秒内**返回，`runs/` 下出现 `plan/` 三个文件，且**没有任何图片或视频**产生。
- 改第 2 镜时长 4→6 秒后点"开始拍摄"，成片里第 2 镜确实是 6 秒，第 3 镜起点相应后移，总时长 = 新值，字幕时间码跟着变。
- 把某一场的一段文字删掉重拆，其余场的镜头**不受影响**（镜号可重排，但内容不变）。
- 手工把某镜时长改成 12 秒，点拍摄应被拒绝，并明确指出"镜 3 超出 10 秒上限"。
- 打开一份**旧版本**（没有 `plan/` 目录、没有 provenance）的运行记录，成片墙与详情页不报错，能正常播放。

## 九、分期

**A. 拆解可单独跑（只读）**：`plan()` + 落盘 + `POST /api/plan` + 拆解页只读展示。
这一期不改任何出图逻辑，风险最低，收益是"终于能看见分镜"。

**B. 可编辑**：`PATCH` 两个接口 + 编辑态 + 校验 + `render()` 从文件读。
这一期开始动引擎的入口，需要回归测试旧路径。

**C. 局部重拆**：按场重派生、受影响镜标记、`stale` 提示。
这一期最难的不是技术，是"改一句话到底该连累哪些镜"的判定规则——先按"同场的镜头"粗放处理，不要一上来做语义级依赖分析。
（已落地，见 §12.6。）

## 十、明确不做

- **不做**富文本剧本编辑器。纯文本加结构，够用；富文本会把这一期的成本翻三倍。
- **不做**分镜的拖拽排序。排序属于时间轴编辑（第三项），这一期只改文字和时长。
- **不做**语义级依赖分析（"改这句台词会影响哪几镜的画面"）。做不到准确，做了反而误导。
- **不引入**新的 LLM 调用。拆解仍然是现有的三次调用，只是把中间结果留下来。
- **不动的**：`output/storyboard.json` 的既有结构、Tkinter 版的行为、`build_timeline` 的算法。

## 十一、风险

| 风险 | 说明 | 应对 |
|---|---|---|
| LLM 输出的 beats 质量不稳 | 模型可能把一拍拆成两句，或漏掉转折 | 拆解后做一次结构校验：场数 ≥2、每场 ≥1 拍、拍数上限 8；不满足则重试一次，仍不满足就降级为"整场一拍" |
| 用户改了分镜但没重算时间轴 | 总时长对不上，合成会错位 | `render()` 强制重算并在界面提示"总时长已从 18s 变为 20s" |
| 旧数据的兼容 | 老 `runs/` 没有 `plan/` | 读不到 `plan/` 时回落到 `output/storyboard.json`，界面显示"这份记录没有拆解信息" |
| 双入口导致行为分叉 | "一次跑完"和"先拆再拍"走不同代码 | 两者共用 `_process_shot` 与 `compose`，只有入口不同；用同一份回归用例各跑一遍 |

## 十二、落地记录

### 12.1 与本文不同之处

设计稿写完到动手之间有几处改了主意，记在这里，免得下次照着文档改错地方。

**没有引入 `Act` / `Beat` 数据类。** 3.1 节写的 `Act`/`Beat` 结构，以及 3.2 节 `Shot` 上的
`act_id` / `beat_ids` / `source_line`，都没有做。`Script.acts` 仍是 `list[dict]`，`Shot.act`
仍是场次名字符串。原因是这三样都要改大模型契约与 `_normalize_storyboard()`，
而 A 期的收益只是"看得见"，用现有的场次名已经够了。**来源可解析**因此退化成按场次名
对齐的粗放判定——这也正是 10 节里"不做语义级依赖分析"的同一条理由。

**没有 `_enforce_narration_pacing()`。** 原设计说 `render()` 要重跑它。实际没有这个函数
（拆解阶段用的是 `llm.distribute_narration()`），而且**重跑一次会把用户逐镜改过的台词整体冲掉**。
落地的是 `Pipeline._check_narration()`：只算"这一镜的字数放不放得下"，放不下就写进
`notes` 与日志，不改写。判据是 `duration × CHARS_PER_SEC × MAX_TEMPO`。

**`render()` 不拿 `brief.total_duration` 当目标时长。** 这是实测踩到的坑：简报里的总时长是
拆解当时的快照，用户把某镜从 5 秒改成 6 秒后，拿它当目标会把 16 秒又压回 15 秒——
**改了等于没改**。目标时长只来自两处：调用方显式指定，或 MV 音频探测值；两者都没有就
沿用分镜自己的累加。

**拍摄复用原 run 目录**（`pipeline/config.py: existing_run_context`）。不新开目录：
plan 与成片要待在同一个 `runs/<run_id>/` 下，否则拆解页手里的 run_id 在拍完之后找不到
自己的成片，成片墙上还会多出一条主题重复的记录。

### 12.2 实际接口

| 方法 | 路径 | 落地说明 |
|---|---|---|
| `POST` | `/api/plan` | 同步调 `Engine().plan()`，落 `plan/` 四个文件 |
| `GET` | `/api/plan/{run_id}` | 读回 project / script / shots / meta |
| `PATCH` | `/api/plan/{run_id}/script` | 改剧本，返回 `stale_shots` 与 `meta`；**不重派生** |
| `PATCH` | `/api/plan/{run_id}/shots/{id}` | 改单镜，返回 `total_duration` / `moved` / `meta`；时长越界当场 422 |
| `POST` | `/api/plan/{run_id}/render` | 202 + `job_id`，与"一次跑完"共用同一套 SSE 事件流 |

`PATCH shots` 返回的 `moved` 是"起点跟着挪了的镜头"。前端按它整表更新 `start`——
只改被改那一行，时间轴显示就会对不上。

`POST render` 会先在 `plan/meta.json` 里写 `rendered: true`，**成片墙据此区分
「只拆没拍」与「拍失败」**。不做这个标记的话，一份刚拆完、还没拍的记录会被三态判成
「失败」并挂在成片墙上——它根本没失败，只是还没拍。判据不能看"有没有 `output/` 目录"：
`ctx.prepare()` 在拆解阶段就把 `output/` 建出来了。

### 12.3 引擎侧

`Pipeline.run()` 被拆成三段，两个入口共用：

```
_prepare_music()  → 音乐探测与节拍     ┐
_env_check()      → FFmpeg 与写盘      ├→ run()          （拆解 + 拍摄）
build_plan()      → 简报/剧本/分镜     ┘

_load_plan()      → 读文件 + 越界校验  ┐
_rebuild_timeline() → 重算 start 与总时长 ├→ render_from_plan()（只拍摄）
_finalize_board() → 歌词上屏 + 落盘    ┘

_render_and_compose() → 逐镜闭环 → 终检 → 合成   ← 两个入口都走这里
```

越界校验跑**两次**：`_load_plan()` 里一次（重算时间轴**之前**，因为重算会把越界值
clamp 回上下限，之后就查不出来了），`_rebuild_timeline()` 里再一次。

### 12.4 已验证

- 改镜 2 时长 5→6 秒后拍摄：成片 `ffprobe` 16.0 秒，镜 3 起点 11.0 秒，SRT 时间码同步变为
  `00:00:11,000 --> 00:00:16,000`。
- 手改 JSON 把某镜写成 12 秒：`POST render` 返回 422，正文指出「镜 3 时长 12s 超出上限 10s」。
- 只改第 2 场文字：`stale_shots` 恰好是 `[2]`，其余场不受牵连。
- 老路径回归：`POST /api/runs`（一次跑完）12 秒 3 镜正常出片，`notes` 为空。

### 12.6 C 期落地记录（按场局部重拆）

**判定规则按原计划粗放处理**：剧本里改的是第 N 场，就只重拆第 N 场，不做语义级
依赖分析。`stale` 仍是"提示"，重拆由人按场发起——按钮只在该场有 stale 镜头、
或该场一个镜头都没拆到时出现。

**接口**：`POST /api/plan/{run_id}/acts/{act_name}/replan`，body `{"force": false}`。

**四条不变量**（都由 `tests/test_pipeline.py` 的 `[9]` 盯着）：

1. **不碰别的场**。其余场次的镜头对象连内容都不改，只在必要时顺移镜号。
2. **总时长不变**。目标时长锁定为"这一场原来的时长之和"，新镜头按这个额度
   重新分配（`build_timeline` 同时把单镜夹回 [2, 10] 秒）。唯一的例外是
   **原本 0 镜的场**：那时从剧本的 `time_range`（`"12-16s"`）读出该场时长，
   补进去会让全片变长，`note` 里明说"16.00s → 20.00s"。
3. **改过的镜头要显式确认**。该场若有 `edited.shots`，默认回 **409** 并列出镜号；
   带 `force=true` 才覆盖。自动覆盖是最不能做的那种"智能"。
4. **镜号顺移要跟着映射**。`edited.shots` / `stale_shots` 存的都是镜号，
   重拆后这一场镜数一变，后面场的镜号就全挪了。`replan_act()` 返回 `id_map`
   （旧镜号 → 新镜号，按对象身份算，新镜头不产生映射），由 `server/plan.py`
   应用到 meta 上。不映射的话"改过"的徽章会标到别的镜头上——徽章错了比没有更糟。

**踩到的坑（值得记）**：单场重拆的解说词一开始全变成「画面还在走。」这类兜底句。
根因是 `split_sentences()` 只按句末标点切，而剧本里一场戏常常就是一整句 30 字的长句，
4 秒镜头的字数硬上限只有 19 字左右，整句塞不进去就被 `distribute_narration()` 整句丢弃
（它宁可少说也不音画错位）。修法是加 `_act_units()`：先按句末切，再把过长的句子
按逗号/顿号拆成小句，保留标点，拼回去仍是通顺原句。

**离线引擎也能重拆**：没有配 Key 时 `_offline_act_shots()` 按目标时长摊镜数、
把本场文字切成小句分配台词、画面描述**直接取自本场文字**（不套题材词库的固定池，
否则"改了但没生效"）。质量不如模型，但"改一句话重拆这一场"这件事本身不需要模型。

## 13. 局部改片（4.5）：单镜重拍与时间轴编辑

拆解层让"拍什么"可改，但改完之后的**代价**没降下来：一条 222 秒的 MV 有 45 镜，
改一镜的画面或改一镜的秒数，都要把 45 镜全渲一遍。改一次等一小时，那"能改"就
只是能改数字。4.5 补的就是这两条降代价的路。

### 13.1 三条路的边界

| 入口 | 重画画面 | 重算镜长 | 复用旧片段 | 接口 |
|---|---|---|---|---|
| 开始拍摄 | 全部 | 是（命中目标总时长） | 否 | `POST /plan/{id}/render` |
| 重拍这一镜 | **只有这一镜** | **否** | 是 | `POST /plan/{id}/shots/{n}/render` |
| 只重合成 | **一个都不画** | **否** | 是 | `POST /plan/{id}/recompose` |

### 13.2 单镜重拍：两条"不做"比"做"更重要

**不重算时间轴**。`_rebuild_timeline` 为了让累加时长命中目标值会微调每一镜，
而其余镜头的片段是按**旧镜长**渲出来的。镜长一动，已有片段与新时间轴就对不上，
成片从被改的那一镜起整体音画错位——而且不报错。所以走 `_sync_starts`：只重排
`start`，一个 `duration` 都不动。代价是总时长可能与目标差零点几秒，这可以接受：
用户点的是"重拍这一镜"，不是"把片子改成 20 秒"。

**不对其余镜头重跑终检**。它们的片段是上一次拍摄的产物，帧缓存可能已经被
`clean_frames` 清掉；重跑终检只会把它们判成"未达标"再按宁缺毋滥原则剔除——
等于用一次单镜重拍把整条片毁掉，而日志上看着还挺合理。

**代码绘制模式直接拒绝**。它按整段分镜编译成 JS 场景再逐帧渲染，没有"只重画一镜"
的入口；跑下去等于整段重画（几十分钟），与预期正相反，中途还没有任何提示。

### 13.3 时间轴编辑：先对齐片段，再拼

`concat_clips` 走 concat demuxer + stream copy，**只认文件本身的长度**，不会照
`start/duration` 去裁。所以改过时长之后必须先把片段本身对齐，否则成片与字幕、
配音、时间轴全对不上，而且不报错，只是越到后面错得越多。

`compose.fit_clip()` 干这件事：长了 `-t` 裁尾，短了 `tpad=stop_mode=clone`
冻结末帧补足。编码参数必须与 `KenBurns.make_clip` 完全一致
（libx264 / preset medium / crf 20 / yuv420p / 30fps）——stream copy 拼不上的
最常见原因就是参数不一致。

对齐结果写 `work/clips_fit/`，**绝不原地覆盖** `work/clips/`：重编码一次画质掉
一次，而且裁短之后再也补不回来。长度差在一帧以内时 `fit_clip` 原样返回源文件，
不为零点几秒白重编码一次。

**重排不改镜号**。`compose` 按传入顺序拼接，所以重排就是把 clips 列表换个次序，
文件名一个都不动。让前端改 `id` 来实现重排，等于把片段文件名、`meta.edited.shots`
的记录、单镜重拍路径上的那一节三处一起改坏。`POST /plan/{id}/shots/reorder`
只收**完整置换**，缺项一律 422——允许缺项就是允许"悄悄删镜头"，成片少两镜而
日志一切正常，是最难查的一类数据丢失。

**配音复用而不是重合成**。台词一个字都没变，重跑一遍 TTS 纯属浪费（云端还要走
网络、还可能失败）。从 `work/vo/shotNN_raw.wav` 取上次的原始配音，只重新
`fit_audio` 到新镜长——镜长变了，拉伸与留白必须跟着变，不重 fit 音画就从这一镜
起错位。原始配音不在时才退回重新合成。

### 13.4 端到端实测（真实数据，2026-10-21）

15 秒 3 镜（每镜 5.0s）的拆解，拍过一次之后：

1. `POST /shots/reorder {"order":[3,1,2]}` → 顺序变 3→1→2，总时长仍 15.00s。
2. `PATCH /shots/1 {"duration":3.0}` → 总时长 13.00s，后面 1 镜起点跟着后移。
3. `POST /recompose` → 25 秒完成，`failed: false`。

结果核对：

- `work/clips/` 三个源片段 md5 **全部未变**（`e0474bdd…` / `0b7343d3…` / `475eaa03…`）
- `work/clips_fit/` 只有 `shot01.mp4`（5.0s → 3.0s），另两镜差在一帧内故原样复用
- `work/concat.txt` 顺序为 `shot03 → clips_fit/shot01 → shot02`
- 成片 13.000s；`output/storyboard.json` 时间轴为 `3@0/5.0`、`1@5/3.0`、`2@8/5.0`
- 日志：`时间轴重合成：3 镜 / 13.00s，1 镜的片段被对齐到新时长（[1]）`
